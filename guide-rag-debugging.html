The Complete Guide to RAG Debugging: Find Where Retrieval Actually Breaks

"The answer is wrong" is not a diagnosis. It's a symptom that could come from five completely different places in a RAG pipeline — chunking, embeddings, retrieval, reranking, or generation — and the most common debugging mistake is jumping straight to the prompt when the actual break is two or three stages upstream.

Here's a systematic pass through all five, in the order to actually check them.

Stage 1: Chunking

Before touching anything downstream, check the chunks themselves.

  • Size vs. content structure — is your chunk size a fixed number chosen arbitrarily, or does it respect actual content boundaries (paragraphs, sections, code blocks)? A fixed 500-token chunk that cuts a table in half produces a chunk that's structurally useless no matter how good your embedding model is.
  • Overlap — too little overlap loses context at boundaries; too much wastes embedding cost on duplicated tokens.
  • Semantic boundaries — does chunking respect where one idea ends and another begins, or does it just count characters?
  • Structured data handling — tables, code blocks, and lists often need different chunking logic than prose. A table chunked mid-row is a chunk with no usable meaning.

Fast diagnostic: pull up 10 random chunks from your index and read them cold, with no other context. If a chunk doesn't make sense on its own, it won't make sense to the retriever or the model either.

Stage 2: Embeddings

  • Domain match — a general-purpose embedding model on highly domain-specific text (legal, medical, internal jargon-heavy docs) is a common silent quality ceiling.
  • Version consistency — if you've changed embedding models or versions, are ALL your vectors re-embedded, or is your index silently mixing two incompatible embedding spaces?
  • Cache invalidation — if chunks change but their embeddings don't get regenerated, you're retrieving against stale content.

Stage 3: Retrieval

This is where most people start debugging — reasonably, since it's the most visible stage — but it's stage 3, not stage 1, for a reason.

  • Hybrid search — pure vector similarity misses exact-match cases (product codes, specific names, acronyms) that keyword/BM25 search catches trivially.
  • k tuning — too low and you miss relevant chunks; too high and you dilute the context with noise.
  • Metadata filtering — is filtering applied before or after the similarity search? Applying it after can filter your top-k results down to fewer than k usable chunks.
  • Adversarial query testing — deliberately try queries phrased differently than your test set (typos, different terminology, indirect phrasing).

Fast diagnostic: for a failing query, print the raw retrieved chunks before they reach the model. Half the time, the generation is actually fine given what it received — the real bug is that retrieval handed it the wrong context in the first place.

Stage 4: Reranking

  • Is one even in the pipeline? A lot of "RAG doesn't work well" reports trace back to no reranker at all.
  • Evaluated separately — has anyone actually measured whether it's helping vs. the base retriever's ordering?
  • Diversity vs. score-stacking — a reranker that just reinforces the top result's neighbors can reduce diversity in edge cases.

Stage 5: Generation

Only now — after chunking, embeddings, retrieval, and reranking are confirmed reasonable — does the generation stage become the likely suspect.

  • Context-only instructions — is the system prompt explicit that the model should answer ONLY from the provided context?
  • Citation enforcement — requiring the model to cite which chunk supports each claim makes hallucination structurally harder.
  • "I don't know" as a valid output — if your prompt doesn't explicitly permit this, the model will often produce a plausible-sounding answer from thin context.
  • Context ordering — some models weight earlier or later context differently ("lost in the middle" effects).

Putting it together

Next time "the answer is wrong" comes in, resist the urge to reach for the prompt first. Print the retrieved chunks. If they're wrong or irrelevant, the bug is upstream (chunking/embeddings/retrieval), and no amount of prompt engineering fixes it. If they're right and the answer is still wrong, now you're actually in generation-stage debugging — with three other stages already ruled out instead of guessed past.
